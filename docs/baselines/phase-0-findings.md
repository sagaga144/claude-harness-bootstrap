# Phase 0 findings (2026-10-10)

Checked on Claude Code 2.1.296, native Windows 11, against the docs as of this date.
The attack matrix itself is in [`hooks-v0.6.1.md`](hooks-v0.6.1.md).

## Headline

The 7 example harnesses generated by v0.6.1 block **0 of 13** attacks with their
hooks. Counting their permission rules, they catch **2 of 13** (`curl` piped into a
shell, and `cat .env`). Their guards work as written: both controls (a plain push and
an edit to `.env`) are blocked in every harness. The gap is coverage, not broken hooks.

## Sandbox (Step 0.1)

- The sandbox runs on macOS, Linux and WSL2 only. **On native Windows, Claude Code runs
  shell commands unsandboxed.** Windows users get only the hook and permission layers.
- Where it runs, it is off by default (`sandbox.enabled`). Writes are limited to the
  working directory and temp, and **protected paths such as `.claude/` stay
  write-denied**, so on macOS, Linux and WSL2 the sandbox already covers shell writes to
  the harness's own files. Network goes through a proxy with an allowlist
  (`sandbox.network.allowedDomains`) that starts empty.
- Hooks, MCP servers and Claude's file tools always run outside the sandbox.
- If the sandbox can't start, commands run unsandboxed unless
  `sandbox.failIfUnavailable` is set.

## Permission rules

- **`ask` rules on `Edit`/`Write` also cover shell writes.** Live test, `dontAsk` mode
  (where `ask` becomes a refusal), rule `Edit(.claude/hooks/**)`:

  | Shell command | Refused |
  |---|---|
  | `sed -i … .claude/hooks/guard.cjs` | yes |
  | `echo hi > …` | yes |
  | `echo hi >> …` | yes |
  | `cp other.txt …` | yes |
  | `tee … < other.txt` | yes |
  | `rm …` | yes |
  | `node -e "require('fs').writeFileSync(…)"` | **no** (the file was wiped) |

  So Step 1.3's Bash hook only needs to cover script runtimes that write files
  themselves (`node -e`, `python -c`, `perl -e`, `ruby -e`, …) and PowerShell.
- **`Read` deny rules also cover `cat`/`head`/`tail` in Bash** (docs). `cat .env` is
  already caught by `Read(.env)`. The roadmap said otherwise; corrected.
- **An explicit `ask` rule can't be silenced for the session.** Tested through the Agent
  SDK, whose permission callback receives the same choices the prompt shows: with
  `ask: ["Edit(.claude/hooks/**)"]`, two edits to two hook files raised two prompts, and
  neither offered a "for this session" option (`suggestions` was empty both times).
  Run first on a temp copy of the monorepo-saas example, then on the real
  `harness-qa/round-04-monorepo-saas` project (restored to clean afterwards). Every
  change to a protected file asks the user, every time.

## Hook paths and the working directory

- The docs say hooks run in the session's current directory, which follows `cd`. With a
  relative command (`node .claude/hooks/x.cjs`), a hook started from a subfolder can't
  find its script; the runner shows every guard in all 7 examples crashing that way
  (Node exits 1, which Claude Code treats as a non-blocking error).
- **Live check: not reproduced.** In three headless Haiku sessions, Claude Code reset the
  shell to the project root after `cd sub`, and every hook ran from the root. So this is
  a hardening fix, not a confirmed live hole. Don't present it as "guards silently off".
- Both `${CLAUDE_PROJECT_DIR}` forms work on Windows: exec form
  (`"command": "node", "args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/x.cjs"]`) and the
  quoted shell form (`node "${CLAUDE_PROJECT_DIR}/.claude/hooks/x.cjs"`).

## Smaller things found

- Several example `settings.json` files set a hook `"timeout": 60000`, and so does the
  spec's own skeleton in `HARNESS_REFERENCE.md` §1.7. Hook timeouts are in seconds
  (docs: "Seconds before canceling", default 600 for command hooks), so that is about
  17 hours, not 60 seconds. A build gate that hangs would hold the session. Fix the
  skeleton to `"timeout": 60` and regenerate the examples.
- No example hook matches the `PowerShell` tool, so on Windows every Bash guard is
  skipped when Claude uses PowerShell instead (A2 shows `·`, no hook).
